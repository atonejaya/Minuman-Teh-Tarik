## Hard constraints (binding for this phase)

1. No production user migration.
2. No change to `src/middleware/auth.middleware.js`.
3. No change to bcrypt-12 (no cost reduction, no algorithm switch).
4. No Worker deploy, no Workers plan upgrade.
5. No request for or use of production credentials.
6. No conclusion that "Supabase already solves Boundary B".
7. Only synthetic/test users and hashes in the disposable/staging project.
8. Password hashes are credential-sensitive: only ever placed in the

## A. Objective

Validate, in a **disposable/staging Supabase project only**, whether the
existing bcrypt-12 hashes (`$2b$12$…`, generated by `bcryptjs` 3.0.3 — the exact
library/version used by the production app) can be:

1. Imported into Supabase Auth without plaintext passwords;
2. Verified successfully by Supabase Auth (`signInWithPassword`);
3. Kept usable (wrong password rejected, hash remains verifiable);
4. Mapped to application identity/role via `user_metadata`;
5. **And — most importantly — prove where password verification executes in the
   candidate architecture: inside Supabase Auth (GoTrue), NOT inside the
   Cloudflare Worker.**

The experiment, not the documentation, is the source of truth.

### Relation to Boundary B (must stay explicit)

The goal of the overall RC1 track is to stop the Worker from executing bcrypt
(cost-12 ≈ 300 ms CPU) against the Workers Free **10 ms CPU/request** limit.

- Moving the **database** to Supabase does **not** by itself move
  `bcrypt.compare()` out of the Worker.
- Moving **password verification** to Supabase Auth **does** — but that must be
  **proven**, not assumed (see §F).

## C. Import Compatibility Matrix

> **Supporting evidence + to-be-verified:** Supabase documentation currently
> documents `password_hash` as a supported Auth migration input for bcrypt
> hashes. Whether the **current hosted Supabase Auth** accepts this project's
> exact `bcryptjs` 3.0.3 cost-12 hashes is **UNVERIFIED** and is executed
> empirically against the disposable project.

### C.1 Assumption under test

```
POST /auth/v1/admin/users
  { email, password_hash: "$2b$12$…", email_confirm: true, user_metadata: {...} }
        │
        ▼
   auth.users row (GoTrue-managed schema; column reported as encrypted_password)
```

- Supabase documentation **currently documents `password_hash` as a supported
  Auth migration input for bcrypt hashes** — its Auth0-migration example uses
  `supabase.auth.admin.createUser({ password_hash })` and lists bcrypt (and
  Argon2) as supported. This is **supporting evidence only**; it does not
  replace the experiment.
- **PHASE 1 independently validates compatibility with this project's exact
  bcrypt-12 hashes (`bcryptjs` 3.0.3, cost 12) against the current hosted
  Supabase Auth behavior** — the disposable project, not the documentation, is
  the source of truth.
- **Status of that assumption: UNVERIFIED until the disposable project
  accepts a bcrypt-12 hash and `signInWithPassword()` succeeds.**
- Note: `auth.users` is **not** exposed via the auto-generated public API;
  direct reads of that schema are only possible via admin/SQL access to the
  staging project (see §E) and are **not** a dependency of the test matrix.

### C.2 Import test cases

| # | Case | Input | Expected PASS | Expected FAIL |
|---|---|---|---|---|
| C1 | Valid bcrypt-12 import | synthetic user, `password_hash` = `$2b$12$…` | Admin create returns user (201); no plaintext in payload response | Admin rejects; no user created |
| C2 | Malformed hash | `password_hash` = `"not-a-hash"` | (document actual behavior) | Import rejected cleanly |
| C3 | NULL / missing hash | no `password_hash` field | (document actual behavior) | Import rejected (or requires a password instead) |
| C4 | Duplicate identity | same email/username imported twice | Second attempt rejected or handled per policy (document) | Duplicate auth.users rows silently created |
| C5 | Import → export round-trip | export created user (admin GET), re-import into a fresh disposable project | Identity/metadata survive; hash still verifiable (§D) | Hash or metadata lost/changed |

### C.3 Commands (runbook, executed only against disposable project)

```text

  -H "Content-Type: application/json" \

        "password_hash": "<bcrypt-12-hash>",
        "email_confirm": true,
        "user_metadata": { "username": "tst_<ts>_owner", "role": "OWNER", "name": "Synthetic Owner" } }'

# 3. List/export created user (admin GET) — identity/metadata round-trip
curl -sS -X GET "$SUPABASE_URL/auth/v1/admin/users" \
  -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"
```

## D. Authentication Verification Matrix

### D.1 Primary proof (hard gate)

| # | Case | Expected PASS |
|---|---|---|
| D1 | Correct password → `signInWithPassword` | HTTP 200, `access_token` + `user` returned |
| D2 | Wrong password → `signInWithPassword` | HTTP 400 `invalid_grant`; no token |
| D3 | Unknown identity → `signInWithPassword` | HTTP 400 `invalid_grant`; no token |
| D4 | Imported hash remains usable | D1 succeeds using the **imported** bcrypt-12 hash (no password re-set) |
| D5 | Resulting JWT valid | `sub` = Supabase `auth.users.id` (UUID); `iss` = `https://<ref>.supabase.co/auth/v1`; `aud` = `authenticated`; `role`/`user_metadata` claims present |

# Wrong password (expected invalid_grant)

## E. Rehash / Hash-Preservation Diagnostic

> **Status: secondary diagnostic, NOT a hard gate.** Rehash behavior on
> sign-in must be documented, but PHASE 1 does NOT depend on reading
> `auth.users.encrypted_password` through a public API (that schema is not
> exposed via auto-generated APIs).

### E.1 Method

- If **admin/SQL access to the disposable/staging project** is available
  (service role / direct Postgres), inspect `auth.users.encrypted_password`
  prefix before and after the first successful login:
  - Before: `$2b$12$…` (or the exact stored prefix)
  - After: same → hash preserved; different prefix/cost → rehash occurred
  - Record the exact before/after prefix and any cost change.
- If such access is **not** available, record that the diagnostic could not be
  performed and proceed on the primary proof (§D) alone.

### E.2 Why it matters

GoTrue may re-hash a password on first successful login to its configured
default (commonly bcrypt cost 10). If so, the migration preserves cost-12 only
until first login, after which the hash may be downgraded. That is a security
property to document — not a blocker for import compatibility, but relevant to
the future security decision.

## F. CPU-Location / Boundary-B Validation

> **This is the decisive experiment.** It distinguishes whether the candidate
> architecture actually removes bcrypt from the Worker (solves Boundary B) or
> merely moves the database while keeping bcrypt in the Worker (Boundary B
> persists).

### F.1 Two candidate architectures (must be kept distinct)

**Architecture 1 — DB-only move (Boundary B persists):**
```
Client
  ↓
Cloudflare Worker Free
  ↓ bcrypt.compare()            ← bcrypt STILL in Worker; ~300 ms CPU > 10 ms limit
Supabase Postgres (only storage)
```

**Architecture 2 — Supabase Auth as authority (Boundary B removed):**
```
Client
  ↓
Cloudflare Worker Free
  ↓ token?grant_type=password   ← HTTP call; NO bcrypt in Worker
Supabase Auth (GoTrue)
  ↓ bcrypt verification         ← bcrypt here, on Supabase infra
```
Only Architecture 2 is the goal of this migration track.

### F.2 What must be proven (evidence, not assertion)

The **proofs below are all mandatory and independent**. Low/absent CPU
measurement alone is **not** sufficient — a request can be cheap for the wrong
reason (e.g. it never actually performed authentication). All must hold.

> **Operational definition of "equivalent password verification":** any
> password-hash verification performed by **application Worker code** — i.e. a
> call that, given a submitted password and a stored password hash, computes
> success/failure inside the Worker runtime (e.g. `bcrypt.compare`,
> `bcrypt.compareSync`, an adapter wrapping them, or a future PBKDF2/argon2
> equivalent). An HTTP call to an external Auth service that performs that
> comparison elsewhere is **not** "password verification by the Worker".

1. **Code-path proof (STATIC):** the candidate Worker verification path imports
   **no** `bcrypt`/`bcryptjs` module and issues **no** `bcrypt.compare()`,
   `bcrypt.compareSync()`, or equivalent password-verification call (as defined
   above) — the only auth action is an HTTP call to
   `POST /auth/v1/token?grant_type=password`. Verified by source inspection of
   the execution path.
2. **Runtime proof (INSTRUMENTATION):** a test hook/spy (instrumentation added
   around any password-verification entry point in the Worker code, e.g. a
   wrapped `compare` or an import-time guard) demonstrates that **no** such
   call is ever invoked on the Worker during an Architecture 2 login. Verified
   by runtime observation, not only by reading the source.
3. **Execution-point proof:** successful sign-in events are attributable to
   Supabase Auth (GoTrue) — e.g. Auth API response/JWT issuance, and (if
   available) staging logs/metrics from the Auth service — not to code running
   in the experiment client/Worker.
4. **Negative proof (must NOT rest on the request failing):** for D2/D3, the
   failure must be attributable to the **Auth authority** (Supabase Auth
   rejected the credentials), **not** to the Worker having executed a local
   password verification that then returned false. A 401/invalid_grant response
   alone is **insufficient** — both "bcrypt never called on the Worker" and
   "bcrypt called on the Worker but comparison failed" produce a failing
   request. The D2/D3 outcome must be paired with proofs (1) and (2): no
   Worker-side verification invocation occurred before/during the failing
   request.
5. **CPU measurement (supporting only; deferred to PHASE 6):** a later staging
   Worker battery measures `cpuTime` via `wrangler tail` correlation (NOT client
   wall-clock) and shows the Supabase-auth path within the 10 ms Free budget
   while the legacy path continues to exceed it. This corroborates the proofs
   above but does **not** substitute for any of them.

### F.3 F-PASS gate (hard gate for the CPU-location question)

**F-PASS requires ALL of:**

- [ ] **Positive proof** — password verification occurs on the **Supabase Auth
       path**, not on the Worker application runtime (F.2.1/F.2.2 source
       absence + F.2.3 attribution).
- [ ] **Negative proof** — proven by BOTH:
       - **Static:** no `bcrypt.compare`, `bcrypt.compareSync`, or equivalent
         password verification (operational definition, F.2 preamble) exists on
         the Worker execution path for the Architecture 2 login (F.2.1); AND
       - **Runtime:** instrumentation/spy shows it is **never invoked** during
         the login (F.2.2) — including on D2/D3 failing requests (F.2.4).
- [ ] **Failure-point attribution** — D2/D3 failures occur at the Auth
       authority, not after a Worker-side local password verification that
       failed (F.2.4).
- [ ] Not solely CPU-observation — the conclusion does not rest on "CPU looks
       low" alone (F.2 preamble).

Only with all four can we state: *"On login through Supabase Auth, the Worker
does **not** perform bcrypt verification"* — which is the Boundary-B-relevant
answer this experiment exists to produce.

### F.4 Explicitly out of scope for PHASE 1

- PHASE 1 does **not** deploy a Worker and does **not** measure Worker CPU.
  It validates the import/verification mechanics **and** fixes the architecture
  distinction above so that PHASE 6 has a correct, unambiguous thing to measure.
- PHASE 1 passing does **not** mean Boundary B is solved. It means the building
  block (Supabase Auth verifying bcrypt-12 outside the Worker) is real.

## G. Acceptance Criteria

**PHASE 1 PASS only if ALL of the following hold:**

- [ ] bcrypt-12 synthetic hash is successfully imported into the disposable
      project (C1; C2–C4 documented without silent corruption).
- [ ] Correct password → `signInWithPassword` succeeds (D1).
- [ ] Wrong password is rejected (D2); unknown identity rejected (D3).
- [ ] Imported bcrypt-12 hash is verifiable without a password reset (D4).
- [ ] No plaintext password exists in any dataset/artifact (B).
- [ ] Disposable dataset integrity 100% (no silent duplication/truncation).
- [ ] No production contact (I).
- [ ] Password-verification path is provable (D5 JWT + endpoint attribution).
- [ ] **F-PASS: static code-path proof + runtime instrumentation proof +
      execution-point attribution + failure-point attribution all hold** —
      Worker runs no `bcrypt.compare`/`bcrypt.compareSync`/equivalent password
      verification (operational definition) on the Architecture 2 login, never
      invokes it at runtime (including on D2/D3 failing requests), and
      verification/failure is attributable to Supabase Auth (F.3), even if the
      measured `cpuTime` proof is scheduled for PHASE 6.
- [ ] Rehash behavior (if any) documented (E).
- [ ] Runbook reproducible from zero (H; no step depends on undocumented state).

**Any FAIL in C1, D1–D4, or the F-PASS gate (F.3) → PHASE 1 FAIL.**

## J. Decision Gate for PHASE 2

### J.1 PASS → PHASE 2 inputs

If PHASE 1 passes, the evidence feeds:

1. **Identity/role mapping design** (`auth.users.id` UUID ↔ `users.id` Int;
   `user_metadata` role/username mapping) — requires the mapping because
   `users.id` is an FK target of ~30 relations (see
   `docs/rc1-supabase-auth-inventory.md` §3.1).
2. **JWT contract** for the Worker side (issuer/audience/sub/role claims from
   D5) and the application identity resolution step.
3. **Dual-auth prototype design** behind `AUTH_PROVIDER=legacy|supabase`
   (default `legacy`), additive route only.
4. **CPU verification plan** (PHASE 6 staging battery using tail-correlated
   `cpuTime`), built directly on §F's architecture distinction.
5. **Migration runbook** for a controlled cutover, incorporating §E rehash
   findings.

### J.2 FAIL → stop

If C1/D1–D4 fail, or the F-PASS gate (F.3) cannot be met, PHASE 1 **FAILS**: do
not design a migration on an unproven import path. Per the directive, **do not
invent workarounds, do not force password resets** — report the incompatibility
and propose the safest alternative for approval.

> **Note:** a D2/D3 401/invalid_grant response alone is **never** sufficient for
> the negative proof (F.2.4) — it must be backed by the static + runtime
> instrumentation evidence. A failing request does not distinguish "bcrypt not
> called" from "bcrypt called but failed".

### J.3 Do NOT do before PHASE 1 execution approval

- ❌ Migrate production users
- ❌ Modify `auth.middleware.js`
- ❌ Change bcrypt-12 (cost/algorithm)
- ❌ Deploy the Worker
